# 陣内どこ？

図形を使った 2 人対戦の推理・陣取りゲーム（React Native + Expo + TypeScript / Android 優先）。

守り側は 3 つの候補から図形を 1 つ選び、フィールド円の 15〜25% を覆うように秘密裏に配置します。
攻め側には図形の種類も位置も知らされず、質問だけが手がかりです。
重なった面積から的中率を求め、100% の陣地をより多く削ったプレイヤーが勝者です。

図形には円や多角形のほか、**動物のかたち**（ねこ・うさぎ・とり・さかな・くま）があり、
イラスト表示とシルエット表示を切り替えられます（当たり判定は同一）。

今回の実装範囲は **1 台の端末で 2 人が交互に操作するローカル対戦（ホットシート方式）** です。
守り側の操作が終わるたびに「端末を渡してください」画面を挟み、図形が相手に見えないようにしています。

## ルールの実装

### ラウンドと配点

- 1 ラウンド = 2 ターン。両プレイヤーが攻め・守りを 1 回ずつ担当します。
- ゲーム開始時に 100% の **配点** をラウンド数ぶんランダムに配分します。
  **合計は必ず 100.00%** です（`distributeScoreWeights`）。
- 配点と守り側の図形面積は独立しています。守り側は配点に関係なく、
  常にフィールドの 15〜25% を覆います。

### 守り側（非公開 + 図形選択 + 被覆率）

- ラウンドごとに **3 つの図形候補** が提示され、守り側はその中から 1 つ選びます。
- 選んだ図形は、フィールド円の **15〜25%（目安 20%）** を覆うように配置します。
- 覆っている面積は「フィールド円の内側だけ」を数えます。円からはみ出した部分は
  画面上も薄く描かれ、採点対象外であることが分かります。
- 選んだ図形の種類・位置・大きさは、攻め側にいっさい知らされません。

### 攻め側（質問と攻撃可能サイズ）

| 有料の質問回数 | 攻撃可能サイズ（基準面積に対する割合） |
| --- | --- |
| 0 回（＝質問 0〜1 回） | 200% |
| 1 回（＝質問 2 回） | 150% |
| 2 回（＝質問 3 回） | 100% |
| 3 回（＝質問 4 回） | 75% |
| 4 回（＝質問 5 回） | 50% |

- **各ターン最初の 1 回の質問は無料** で、攻撃可能サイズが下がりません
  （`FREE_QUESTIONS_PER_TURN`）。
- 攻撃可能サイズは守り側の「実際の」面積ではなく基準値（20%）から計算します。
  実際の値を使うと、攻撃可能サイズから守り側の面積が逆算できてしまうためです。
- 攻め側は図形の種類も自分で選びます（守り側の候補とは無関係）。

### 判定

```
的中率 (%)     = 重複面積 ÷ 守り側の被覆面積 × 100
今回削った割合 = ラウンドの配点 × 的中率 ÷ 100
```

累計した「削った割合」が高いプレイヤーの勝ちです（満点は 100%）。

### 面積・重複の計算方法

幾何図形（円・楕円・三角形・四角形・五角形・六角形）はすべて凸ですが、
動物図形は凹形状を含みます。そこで、

1. 動物図形の輪郭を **耳刈り法で三角形に分割**し、互いに素な凸パーツ集合にする
2. 円・楕円も十分細かいポリゴン（既定 240 分割）に変換する
3. すべての面積・重複計算を、この凸パーツ集合の上で
   **Sutherland–Hodgman の凸多角形クリッピング**で行う

という方針に統一しています。その結果、

- 描画に使う図形と採点に使う図形が完全に一致します
- パーツが互いに素なので、重なりを二重に数えることがありません
- フィールド円でのクリップも同じ仕組みで扱えます
- 守り側と攻め側がまったく同じ図形を置いた場合の的中率は 100.00% になります

複数図形の和集合が必要な場合は `unionArea` が「凸どうしの差集合」を使って
重なりを打ち消しながら厳密に計算します（`subtractConvex`）。

### 情報の非公開

攻め側の画面（質問・攻撃配置）は `GameState` を直接参照せず、
`visibility.ts` の `attackerView()` が返す **AttackerView 型** だけを使います。
この型には守り側の図形・配置条件・図形候補が構造的に含まれないため、
UI の実装ミスで秘密情報を表示してしまうことがありません。

`findDefenseLeaks()` は、与えられたデータに守り側の秘密（図形の座標・サイズ・
回転・種類・条件のパラメータ）が混ざっていないかを走査するテスト用関数です。

### 配置条件を追加する

`src/domain/types.ts` の `ConditionKind` に種類を足し、
`src/domain/conditions.ts` の `CONDITION_DEFS` に定義を 1 つ追加するだけです。

```ts
my_new_condition: {
  kind: 'my_new_condition',
  shortLabel: '短いラベル',            // ホーム画面のカスタム設定用
  describe: () => 'ラウンド開始画面に出す説明',
  checkLabel: () => '守り側のチェックリストに出す文言',
  test: (geometry) => /* 判定（geometry は輪郭 + 凸パーツ集合） */,
  create: (rng) => ({ kind: 'my_new_condition' }),  // ランダム生成時のパラメータ

```

判定には `ShapeGeometry`（輪郭と凸パーツ集合）が渡されるため、

判定ロジックのほかに UI を書き足す必要はありません。
ホーム画面のカスタム設定・ラウンド抽選・守り側のチェックリストは
すべてこのレジストリから自動生成されます。

`src/domain/questions.ts` の `QUESTION_DEFS` に 1 件足すだけです。
回答は守り側プレイヤーではなくシステムが図形データから自動判定します。

## 実装上の仮定

仕様書に明記がなく、実装のために判断した点です。いずれも設定値・レジストリ化してあるため後から変更できます。

1. **フィールドは円形、原点はその中心**。
   補助線として X 軸・Y 軸と、「フィールド面積の 50% を持つ正方形」を表示しています。

2. **守り側の図形は 1 つ**とし、「移動・回転・サイズ変更」で配置します。
   被覆率の計算（`coveredArea`）は図形の配列を受け取り、重なりを打ち消す
   和集合として実装してあるため、将来複数図形を置けるようにしても計算は変わりません。

3. **図形はフィールド円からはみ出してもよい**が、はみ出した部分は面積に数えません。
   極端な配置を防ぐため、図形の中心はフィールド内にある必要があります。

4. **ラウンドの配点と守り側の面積は別物**です。
   元の仕様では「ラウンドの面積割合」が守り側の図形面積を兼ねていましたが、
   被覆率が 15〜25% に固定されたため、配点は得点の重みとしてのみ使います。
   全ラウンドの配点合計が 100% になる点は変わりません。

5. **攻撃可能サイズの基準は 20%（DEFENSE_COVERAGE.target）**です。
   守り側の実際の被覆率を使うと、攻撃可能サイズから相手の面積が逆算できてしまいます。

6. **攻め側は自分で図形の種類を選べます**。
   守り側の図形が非公開になったため、攻め側の図形を守り側に合わせることができません。
   配置条件の制約も受けず、サイズ上限と「中心がフィールド内」だけが条件です。

7. **配置条件は守り側だけに提示されます**。条件も攻め側にとっては推理対象です。
   結果画面で公開されます。

8. **「指定領域」の定義**は 4 象限 / 補助正方形の内側・外側 / X 軸より上 / Y 軸より右
   としました（`src/domain/regions.ts`）。

9. **配置不可能な出題はしない**。
   ラウンド生成時に「その条件で被覆率 15〜25% を満たす配置」が実在するかを
   配置探索で確認し、成立しない図形は候補に出しません。
   守り側の初期配置と「おまかせ配置」にも同じ探索を使うため、詰むことはありません。

10. **動物図形の装飾（目・鼻・耳の内側など）は描画専用**です。
    当たり判定・面積計算に使うのは輪郭だけなので、イラスト表示とシルエット表示で
    判定ジオメトリは完全に同一になります（selftest で検証）。

11. **スコアの可視化は「プレイヤーごとに 100% の陣地」**としました。
    両者の累計は独立に 0〜100% を取りうるため、ドーナツを 2 つ並べています。

12. **同点の場合は引き分け**。

13. **画面遷移にナビゲーションライブラリを使わない**。
    進行が一本道のステートマシンであり、依存を増やさないほうが起動時エラーのリスクも下がるためです。

## 図形を追加する

### 動物図形

`src/domain/animals.ts` の `RAW_ANIMALS` に 1 件足し、`AnimalKind` に種類名を加えるだけです。

- `outline`: 輪郭。自己交差していない単純多角形であれば凹んでいて構いません。
  座標スケールは任意で、読み込み時に「重心が原点・最遠点までが 1」に正規化されます。
- `details`: 目・鼻などの装飾。`dot` / `poly` / `line` を同じ座標系で指定します。
  **描画にしか使われない**ので、当たり判定への影響を気にする必要はありません。

`npm run selftest` が輪郭の自己交差・三角形分割の整合性・正規化を自動で検証します。

## 今後オンライン対戦にする場合

- `src/domain/` は純粋関数と reducer のみで構成されており、そのままサーバーで動きます。
- `GameState` はシリアライズ可能なデータのみを保持しています。
- ラウンド生成はシード（`GameState.seed`）から決まるため、
  サーバーがシードを配るだけで両端末が同じ出題を再現できます。
- 秘密情報（`defenseShape` / `RoundSpec.condition` / `RoundSpec.shapeCandidates`）を
  取り除いたペイロードはすでに `visibility.ts` の `attackerView()` として実装済みです。
  攻め側の端末へはこのビューをそのまま送ればよく、サーバー側の実装がほぼそのまま流用できます。
- 動物図形の装飾は描画専用で判定に関与しないため、サーバーは輪郭データだけを持てば十分です。
